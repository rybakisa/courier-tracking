# 1. Мониторинг и наблюдаемость

Принцип: **каждая метрика привязана к требованию**. Поверх этого — рамка **Four Golden Signals** (Google SRE):
для каждого ключевого сервиса смотрим **Latency / Traffic / Errors / Saturation**, чтобы не осталось слепых зон.

- **Headline-сигнал — сквозная свежесть** (ping → экран): это user-facing **Latency** горячего пути, на ней
  главный SLO и алерт (§2).
- **Saturation** — USE по компонентам, узкие места из артефакта 06 (§4).
- **Traffic / Errors** — спрос и доля сбоев на каждой границе; раньше были недосказаны — делаем явными (§3).
- Сверх 4GS — **сигналы отказов** (FT-оверлей: промоут реплики, шторм реконнектов, ребаланс): сработало ли
  переключение (§5).

Горячий/холодный путь дают и разделение симптомов: у горячего — **задержка**, у холодного — **полнота**.

---

# 2. Headline Latency — сквозная свежесть (на серверных часах!)

Свежесть «ping → экран» — то, что обещаем клиенту, и что первой деградирует под нагрузкой (артефакт 02).

**Критично: `t0` — серверное время приёма (Connection Manager штампует пинг на входе), а НЕ `ts` устройства.**
Часы телефона скошены — разностью с device-`ts` мерить свежесть нельзя (получишь фикцию вплоть до
отрицательной). Device-`ts` нужен для **порядка трека** (история), не для свежести.

Чтобы не вычитать время между разными узлами (у курьера и наблюдателя — разные CM), меряем **по стадиям**,
каждую в своём clock-домене, и **суммируем длительности** (трассировка с семплированием: один из N пингов
несёт trace-id сквозь стадии):

```
  ① сеть курьер→CM                         (оценка по client RUM / RTT)
  ② CM: приём → produce
  ③ лог: append/durable-ack (acks=all)
  ④ Live: забрал из лога                    (consumer lag)
  ⑤ Live: индекс + fan-out/кластеризация → publish в шину
  ⑥ шина → CM подписчика → push в сокет
  ⑦ сеть CM→наблюдатель + рендер            (client RUM, с поправкой на skew)
```

②–⑥ — **серверные**, единицы–десятки мс, меряются точно. Основной вклад дают сетевые ①/⑦ (мобильный канал) —
их оцениваем клиентским RUM с поправкой на часы через RTT, а **не** вычитанием device-`ts`. SLO якорим на
серверной части (②–⑥); полная staleness — вторичная RUM-оценка.

# 3. Four Golden Signals по сервисам

Матрица «сервис × L/T/E/S» — страховка покрытия. **Latency** горячего пути — это §2; **Saturation** детально —
§4; **Traffic** и **Errors** сводим здесь явно.

| Сервис | Latency | Traffic | Errors | Saturation (§4) |
|---|---|---|---|---|
| **Connection Manager** | push в сокет; handshake-latency | активные WS, новые конны/с, push-сообщ/с | WS close-коды (4001/4003/4008), отказы хендшейка, churn реконнектов | conn/узел, CPU/mem |
| **REST API Service** | p99 по `/position`,`/route`,`/history`,`/pings` | RPS по эндпоинтам, доля fallback-ingest | 5xx, 4xx, 429, доля `503 DEGRADED` | инстансы/CPU за LB |
| **Лог (Kafka)** | produce-latency, append→`ack` | сообщ/с (ingest), по партициям | produce-fail, under-replicated, ISR-shrink | лаг/throughput **по партициям** |
| **Live + fan-out** | ④ consumer lag, ⑤ fan-out/кластеризация | notify/с, снапшотов/с, re-subscribe/с | notify без подписчика, ошибки кластеризации | CPU гео-индекса, **лаг реплики** |
| **Pub/Sub шина** | publish→deliver latency | publish/с | доля недоставленных (no-subscriber) | throughput шины |
| **Cold-store** | latency записи/чтения (FR4/FR5) | запись/с (по политике), read RPS | ошибки/таймауты записи-чтения | диск/узел, compaction |

**Errors — теперь первоклассный сигнал:** всплеск 5xx / WS-close-кодов / `503` / produce-fail / no-subscriber —
это пользовательский симптом, и на него алертим (§6), не только на свежесть. **Traffic** — знаменатель и
драйвер: аномалия = либо рост спроса, либо баг; служит сверкой с расчётами артефакта 02 на реальных числах.

# 4. Saturation (USE) — детально

Узкие места из артефакта 06 — то, что упрётся первым. Алертим по порогам ёмкости:

| Компонент | Utilization / Saturation | Зачем |
|---|---|---|
| **Connection Manager** | conn/узел, CPU/mem, push-сообщ/с, churn реконнектов | ёмкость соединений (NFR5); потолок 20K/узел |
| **Лог (Kafka)** | лаг и throughput **по партициям** (не агрегат) | поймать **горячую партицию** (мегаполис, 06 §3) |
| **Live-узел** | CPU, ops/с гео-индекса, mem, **лаг реплики** | готовность к failover (06 §5); перегрев индекса |
| **Pub/Sub шина** | publish/с, latency, **доля notify без подписчика** | subscriber-gap/churn; перегруз раздачи |
| **Cell-churn** | смен ячейки / re-subscribe в секунду | шторм пан/зума или быстрые движенцы (06 §4) |
| **REST API Service** | RPS, latency, 5xx, **доля fallback-ingest** | всплеск fallback = деградация WS-пути |
| **Cold-store** | latency записи/чтения, compaction, диск/узел | ёмкость архива (06 §7) |

# 5. Сигналы отказов (отказоустойчивость)

Явно следим, что отказ случился **и переключение сработало** (механизмы из 06 §2/§5/§6):

| Сигнал | Что значит |
|---|---|
| **Промоут реплики Live** / рост лага реплики | primary Live упал → реплика встала; лаг реплики = риск «холодного» failover |
| **Шторм реконнектов** на CM | выпал узел/зона — десятки тысяч ломятся; проверяем, что запас ×2 держит |
| **Ребаланс consumer-group** | инстанс консюмера умер/добавился — всплеск лага на время ребаланса |
| **Notify без подписчика** в шине (всплеск) | массовый subscriber-gap (выпал CM-инстанс) |
| **Здоровье региона** | golden signal в разрезе региона (NFR4) — деградация часто локальна |

# 6. SLO, SLI и бюджет ошибок

SLO без **SLI** (чем именно измеряем) — лозунг. Фиксируем измеримый индикатор:

| SLO | SLI — как меряем | Цель | Окно / бюджет |
|---|---|---|---|
| **Доступность** клиентского read-пути | доля успешных проб: WS-connect + первый кадр < X **или** `GET /position` 2xx < X (синтетика по регионам + реальный success-ratio) | 99.99% (NFR5) | 30 дней / ≈4.3 мин/мес |
| **Свежесть** клиента | доля кадров с E2E (②–⑥) < 1 с | 99% | 30 дней / 1% вне цели |
| **Durability** приёма | `acked ⟹ durable` (0 потерь после `ack`) + архив полон по политике (сверка) | жёстко | бюджета нет — инвариант |

Операторский флоу — отдельный, более мягкий SLO по свежести (секунды, не суб-секунда; NFR1). История — SLO
про **полноту**, не latency.

**Что ест бюджет.** `503 DEGRADED` с откатом на чтение последней точки (артефакт 03 §5) — **частичный** расход
бюджета доступности, не полный отказ: клиент видит позицию, теряет лишь живость. Сознательный размен:
durability важнее живости.

# 7. Алерты — на симптомы и на отказы

Алертим на **симптомы у пользователя** (burn-rate) + на **подтверждённые отказы**; сатурация — вторично, на дашборды.

| Алерт | Условие | Почему |
|---|---|---|
| Свежесть деградирует | burn-rate бюджета свежести (мульти-окно: 5 мин + 1 ч) | клиент видит лаги «здесь и сейчас» |
| **Рост ошибок** | всплеск 5xx / WS-close / `503` / produce-fail / no-subscriber (burn-rate) | пользователь видит сбои/деградацию (Errors-сигнал) |
| Durability под угрозой | under-replicated партиции / produce-fail **ИЛИ** расхождение полноты архива | риск необратимой потери |
| CM насыщается / шторм реконнектов | conn/узел > 18K **ИЛИ** всплеск реконнектов | предвестник отказа соединений |
| Лаг live / реплики Live | live-консьюмер > 2 с **ИЛИ** реплика Live отстаёт | «горячая картинка стареет» / риск холодного failover |
| Регион деградирует | golden signal региона вне цели | локальная деградация (NFR4) |

**Burn-rate, а не статичный порог:** ловим и резкий инцидент (→ страница дежурному), и медленную утечку
бюджета (→ тикет), не дёргая дежурного по разовым выбросам.

# 8. Дашборды (контекст для разбора)

Не алертим, но без этого метрики не читаются:

- **Бизнес-пульс:** онлайн-курьеры, активные клиент/оператор-сессии — знаменатель нагрузочных метрик
  (Traffic) и сверка с расчётами артефакта 02.
- **География:** свежесть/нагрузка/отказы по регионам (NFR4) — деградация часто локальна.
- **Hot-доля:** сколько курьеров «горячие» (под клиентским наблюдением, ≈4 с) — драйвер fan-out/ingest.
- **Out-of-order / доля дублей:** **не алерт** — с идемпотентностью по `(courierId, installId, seq)` дубли
  безвредны; аномальный рост — повод посмотреть (реинсталлы, кривой клиент).

**Вывод.** Наблюдаемость повторяет архитектуру и накрыта рамкой **Four Golden Signals**: headline — E2E-свежесть
(**Latency** горячего пути, на серверных часах); **Saturation** — USE по узким местам 06; **Traffic/Errors**
сведены по сервисам; durability — отдельно и по полноте (`acked⟹durable` + архив по политике); сверху —
**сигналы отказов** под отказоустойчивую топологию. Алерты — на burn-rate пользовательских SLO и подтверждённые
отказы. Этим семь артефактов замыкаются: от требований (01) к доказательству в проде (07).
