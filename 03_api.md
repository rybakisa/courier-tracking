# 1. Выбор протоколов (REST + WebSocket)

API закрывает три потребности:

1. **Отправка** — курьерское приложение шлёт своё местоположение.
2. **Приём в реальном времени** — клиенты и диспетчеры видят живые координаты.
3. **История** — чтение маршрута за сегодня и за прошлые дни.

Ниже концептуальное обоснование для каждого пункта.

## 1.1 Отправка (WebSocket)

Как альтернатива рассматривался REST-запрос на каждый пинг). Отказываемся по следующим причинам:
- частые HTTP запросы: TCP+TLS-хендшейки ради передачи всего лишь ≈50 байт
- не выигрываем по расходу энергоресурса клиентского девайса: после каждого запроса устройство ещё несколько секунд держится в высоком энергосостоянии, поэтому при отправке раз в пару секунд оно почти не засыпает и не экономит заряд

Преимущества WebSocket:
- один хендшейк на всё соединение, не грузим клиент и сервер
- при необходимости можно перейти на гораздо более частый обмен данными

## 1.2 Приём в реальном времени (WebSocket)

Частота обновлений переменная (зависит от ситуации), поэтому наблюдателю логично получать события
по мере появления (server-push), а не опрашивать сервер с фиксированной частотой.
К тому же, поллинг при 200K сессий — это сотни тысяч
пустых запросов в секунду.

Также, как альтернативу здесь можно использовать gRPC-streaming для имплементации серверных событий

WebSocket даёт нам серверные события и при этом нативен в браузере (в отличие от, например, gRPC-streaming, который можно).

## 1.3 История (REST)

Максимально органично для REST:
- ресурсная модель для предметной области (курьеры, координаты)
- редкие запросы по требованию
- повсеместный HTTP стек и тулинг, в том числе на клиентах

## 1.4 Другие протоколы

- **GraphQL** отмели, так как:
  - не нужен гибкий выбор полей на клиенте: всегда отдаём данные фиксированной формы;
  - сложность имплементации и мониторига;
- **gRPC** отмели, так как:
  - идеологически не ложится на домен (не вызываем удалённые процедуры, а просто шлём поток данных)
  - хорош для real-time, но ради него не хотим жертвовать нативностью WebSocket для браузеров

# 2. Отправка положений курьером (FR1)

**Задача.** Курьерские приложения непрерывно поставляют местоположение: ≈300K устройств онлайн,
пинг раз в 3–5 с, ≈75K сообщений/с на пике. Три ограничения тянут в разные стороны: данные нельзя
терять (durability, NFR-2); свежесть нужна разная — суб-секундная, когда за курьером следят, и
необязательная, когда нет; и это мобильные устройства, где дорог каждый процент батареи.

**Решение.**

- Постоянный WebSocket вместо запроса на каждый пинг (§1) — один хендшейк, обратный канал,
  экономия батареи.
- Частота отправки адаптивная по двум независимым осям: **движение** решает само устройство
  (стоит → редко, едет → чаще), **наблюдение** — сервер поднимает частоту, когда за курьером
  следят, и отпускает после кулдауна.
- Durability: сервер шлёт `ack` только после durable-записи; устройство буферит неподтверждённое
  и переотправляет при реконнекте; дедуп по `(courierId, seq)`.
- Один поток на сервере раздваивается: живая раздача наблюдателям (по спросу) и **безусловная**
  запись в историю.

| Состояние | Частота отправки | Кто решает |
|---|---|---|
| Стоит, не наблюдают | ≈60 с | устройство (по движению) |
| Едет, не наблюдают | ≈10–15 с | устройство (по движению) |
| Наблюдают | ≈4 с | сервер (`config`) |

**В контракте.** WebSocket `wss://…/v1/stream/courier?ticket=…`.

```jsonc
{ "op": "ping", "seq": 1042, "ts": "…", "lat": 55.7512, "lon": 37.6184 } // курьер → сервер
{ "op": "ack",    "throughSeq": 1042 }                  // сервер → курьер: записано durable
{ "op": "config", "sendIntervalMs": 4000 }              // сервер → курьер: частота при наблюдении
```

Fallback, где постоянное соединение невозможно: `POST /couriers/{id}/pings` (батч +
`Idempotency-Key`). В Swagger — раздел **«Курьер — отправка положений»**.

# 3. API диспетчера (FR3–FR5)

**Задача.** Диспетчер наблюдает не за известным курьером, а за **произвольным набором в области
карты**. В плотном центре в один вьюпорт попадают тысячи курьеров — наивная раздача даёт до
гигабит/с (расчёты, §6) и нечитаемую кашу на экране. Плюс диспетчеру нужны исторические чтения:
маршрут за сегодня и за прошлые дни.

**Решение.**

- Подписка на **область** (bbox + zoom), а не на курьера.
- **Серверная кластеризация** плотных зон (≈150 маркеров на вьюпорт независимо от плотности) —
  одновременно делает экран читаемым и схлопывает fan-out.
- Живой вьюпорт — push по WebSocket (дельты на вход / выход / движение); первичный снапшот и
  история — REST (кэш, пагинация).
- «Горячими» (§2) становятся только индивидуально отрисованные курьеры, не свёрнутые в кластер.

**В контракте.** WebSocket `wss://…/v1/stream/dispatcher?ticket=…`.

```jsonc
{ "op": "viewport", "bbox": [37.55, 55.70, 37.70, 55.80], "zoom": 12 }       // диспетчер → сервер
{ "type": "clusters",      "cells": [ … ], "markers": [ … ] }                // сервер: первый набор
{ "type": "clusterUpdate", "moved": [ … ], "left": [ … ], "entered": [ … ] } // сервер: дельты
```

REST: `GET /viewport?bbox=&zoom=` (снапшот), `GET /couriers/{id}/route?date=` (FR4),
`GET /couriers/{id}/history?from=&to=` (FR5; retention 1 год). В Swagger — раздел **«Диспетчер»**.

# 4. API клиента (FR2)

**Задача.** Получатель заказа следит за **одним конкретным** курьером, и нужно «как в такси» —
плавно и живо, суб-секундное ощущение. Это самый массовый сценарий (≈200K сессий на пике), но
дешёвый по раздаче: fan-out ≈ 1 (один курьер → один клиент).

**Решение.**

- Подписка на одного известного курьера; она же — **сигнал «наблюдают»**, который переводит
  курьера в горячий режим и включает live-раздачу его пингов (§2).
- Первая отрисовка — мгновенно из последней известной точки (REST), дальше живые кадры по
  WebSocket.
- Плавность — **клиентской интерполяцией** между пингами; сервер не обязан слать суб-секундно.

**В контракте.** REST `GET /couriers/{id}/position` (первая отрисовка) + WebSocket
`wss://…/v1/stream/client?ticket=…`.

```jsonc
{ "op": "subscribe", "courierId": "c_123" }                                      // клиент → сервер
{ "type": "snapshot", "courierId": "c_123", "lat": …, "lon": …, "online": true } // первый кадр
{ "type": "position", "courierId": "c_123", "lat": …, "lon": … }                 // далее — живые
{ "type": "status",   "courierId": "c_123", "online": false }                    // ушёл оффлайн
```

В Swagger — раздел **«Клиент»**.

# 5. Покрытие требований

Проверка, что API на этом этапе закрывает требования и не противоречит сам себе.

| Требование | Где в API |
|---|---|
| FR1 — приём геопозиции | §2: WebSocket-ingest + REST-fallback |
| FR2 — слежение клиента за курьером | §4: WS-подписка + `GET /position` |
| FR3 — курьеры в области (диспетчер) | §3: WS-вьюпорт + `GET /viewport` |
| FR4 — маршрут за сегодня | §3: `GET /couriers/{id}/route` |
| FR5 — история за период | §3: `GET /couriers/{id}/history` |
| NFR1 — свежесть | server-push по WS, частота отправки ≈4 с при наблюдении, интерполяция; история к задержке не критична |
| NFR2 — durability 1 год | безусловная durable-запись, `ack` после записи, реплей; за пределами года — `410` |
| NFR3 — согласованность | live — eventual (`asOf`, `stalenessMs`); история — полная и непротиворечивая |
| NFR4 — гео-распределённость | региональные стримы (наблюдатель обычно в регионе курьера), REST кэшируется/CDN |
| NFR5 — uptime 99.99% (клиент) | вклад API: `503 DEGRADED` + чтение последней точки; целиком — в масштабируемости (артефакт 06) |

Противоречий нет. Ключевая развязка: свежесть (NFR1) и durability (NFR2) разведены на горячий и
холодный путь — живой стрим может деградировать, история durable всегда. Адаптивная частота отправки влияет
на **гранулярность** записи у ненаблюдаемых курьеров, но не на потерю точек. Единственный открытый
продуктовый вопрос — нужна ли частая гранулярность для курьера на активной доставке, за которым в
этот момент никто не смотрит (потребовал бы внешнего сигнала о заказе, который вне скоупа).
