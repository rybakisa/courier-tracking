Получился достаточно специфичный API с разными решениями, которые хочется учесть в расчетах, поэтому API будет разобран до расчетов.   
Полная REST-спека — **[Swagger UI](/api-spec)**.

# 1. Выбор протоколов (REST + WebSocket)

API закрывает три потребности:

1. **Отправка** — курьерское приложение шлёт своё местоположение.
2. **Приём в реальном времени** — клиенты и операторы видят живые координаты.
3. **История** — чтение маршрута за сегодня и за прошлые дни.

Ниже концептуальное обоснование для каждого пункта.

## 1.1 Отправка (WebSocket)

Как альтернатива рассматривался REST-запрос на каждый пинг.

Отказываемся по следующим причинам:
- частые HTTP запросы: TCP+TLS-хендшейки ради передачи всего лишь ≈50 байт
- не выигрываем по расходу энергоресурса клиентского девайса: после каждого запроса устройство ещё несколько секунд держится в высоком энергосостоянии, поэтому при отправке раз в пару секунд оно почти не засыпает и не экономит заряд

Преимущества WebSocket:
- один хендшейк на всё соединение, не грузим клиент и сервер
- при необходимости можно перейти на гораздо более частый обмен данными

## 1.2 Приём в реальном времени (WebSocket)

Частота обновлений переменная (зависит от ситуации), поэтому наблюдателю логично получать события
по мере появления (server-push), а не опрашивать сервер с фиксированной частотой.

Также, как альтернативу здесь можно использовать gRPC-streaming для имплементации серверных событий, 
но WebSocket даёт нам серверные события и при этом нативен в браузере (в отличие от, например, gRPC-streaming, который можно).

## 1.3 История (REST)

Максимально органично для REST:
- ресурсная модель для предметной области (курьеры, координаты)
- редкие запросы по требованию
- повсеместный HTTP стек и тулинг, в том числе на клиентах

## 1.4 Другие протоколы

- **GraphQL** отмели, так как:
  - не нужен гибкий выбор полей на клиенте: всегда отдаём данные фиксированной формы;
  - сложность имплементации и мониторига;
- **gRPC** отмели, так как:
  - идеологически не ложится на домен (не вызываем удалённые процедуры, а просто шлём поток данных)
  - хорош для real-time, но ради него не хотим жертвовать нативностью WebSocket для браузеров

# 2. Отправка положений курьером (FR1)

## Задача
Курьерские приложения непрерывно поставляют местоположение. Три ограничения тянут в разные стороны:
- данные нельзя терять (NFR-2)
- суб-секундное ощущение при слежении за курьером
- на курьерском девайсе дорог каждый процент батареи

## Принятые решения

- Постоянный **WebSocket** вместо запроса на каждый пинг.
- Частота отправки курьером координат **адаптивная** по двум независимым осям:
  - движение: решает само устройство (стоит → редко, едет → чаще),
  - факт наблюдения: сервер поднимает частоту, когда за курьером следят, и отпускает после кулдауна

| Состояние                    | Частота отправки | Кто решает               |
|------------------------------|------------------|--------------------------|
| Курьер стоит, нет наблюдения | ≈60 с            | устройство (по движению) |
| Курьер едет, нет наблюдения  | ≈10–15 с         | устройство (по движению) |
| Есть наблюдение              | ≈4 с             | сервер                   |

- **Durability**:
  - сервер шлёт `ack` после durable-записи в лог (Kafka `acks=all`, `min.insync.replicas` ≥ 2, RF 3);
    устройство буферит неподтверждённое и переотправляет при реконнекте;
  - REST Fallback, где постоянное соединение невозможно:
    - `POST /couriers/{id}/pings` (батч + `Idempotency-Key`);
    - подробнее в раздел «Курьер — отправка положений» в Swagger
- **Consistency**: дедуп данных на сервере по метаданным с девайса курьера, например, `(courierId, installId, seq)`, подробнее ниже
- **Availability**:
  - отдельный "горячий" контур для стриминга позиций клиентам и операторам
  - Server-push приходит по мере событий для клиента и с дебаунсом в 1 секунду для оператора, чтобы устройство оператора успевало обрабатывать.

## Контракты
WebSocket `wss://…/v1/stream/courier?ticket=…`.

Все WS-кадры — это JSON с единым полем-дискриминатором `type`;   
Версия протокола зафиксирована в пути (`/v1/`);

```json
// курьер → сервер
{
  "type": "ping",
  "seq": 1042,
  "ts": "…",
  "lat": 55.7512,
  "lon": 37.6184
}

// сервер → курьер: записано durable
{
  "type": "ack",
  "throughSeq": 1042
}

// сервер → курьер: частота при наблюдении
{
  "type": "config",
  "sendIntervalMs": 4000
}             
```
Дополнительные метаданные:
- `installId` — идентификатор установки приложения; курьер предъявляет его при открытии стрима
- Ключ дедупа = `(courierId, installId, seq)`
- при переустановке `seq` сбрасывается, но меняется `installId`, поэтому новые точки не схлопываются со старыми

# 3. API оператора (FR3–FR5)

## Задача
Оператор наблюдает не за известным курьером, а за произвольным набором в области карты.
В плотном центре в один вьюпорт попадают тысячи курьеров. Наивная раздача даёт до гигабит/с и нечитаемую кашу на экране.
Плюс оператору нужны исторические чтения: маршрут за сегодня и за прошлые дни.

## Принятые решение

- Подписка на область (bbox + zoom), а не на курьера.
- **Серверная кластеризация** плотных зон (≈150 маркеров на вьюпорт независимо от плотности), одновременно делает экран читаемым и схлопывает fan-out.
- Живой вьюпорт: push по WebSocket: **полный снапшот** вьюпорта периодически (≤150 маркеров, не дельты, обоснование в артефакте 05 §7);
- «Горячими» становятся только индивидуально отрисованные курьеры, не свёрнутые в кластер.
- История:  REST API.

## Контракты
WebSocket `wss://…/v1/stream/operator?ticket=…`.

```json
// оператор → сервер
{
  "type": "viewport",
  "bbox": [37.55, 55.70, 37.70, 55.80],
  "zoom": 12
}

// сервер: полный снапшот вьюпорта, периодически (≤150)
{
  "type": "clusters",
  "cells": [ … ],
  "markers": [ … ]
}   
```

REST (раздел **«Оператор»** в Swagger):
- `GET /viewport?bbox=&zoom=` (снапшот)
- `GET /couriers/{id}/route?date=` (FR4),
- `GET /couriers/{id}/history?from=&to=` (FR5; retention 1 год)

# 4. API клиента (FR2)

## Задача
Получатель заказа следит за **одним конкретным** курьером, и нужно «как в такси», суб-секундное ощущение.
Это самый массовый сценарий (≈200K сессий на пике), но дешёвый по раздаче: fan-out ≈ 1 (один курьер → один клиент).

## Приянтые решения
- Подписка на курьера (она же факт наблюдения), которая переводит курьера в горячий режим и включает live-раздачу его пингов (§2).
- суб-секундного ощущения достиаем **клиентской интерполяцией** между пингами; сервер не обязан слать суб-секундно.

## Контракты
WebSocket `wss://…/v1/stream/client?ticket=…`.

```json
// клиент → сервер
{
  "type": "subscribe",
  "courierId": "c_123"
}

// первый кадр
{
  "type": "snapshot",
  "courierId": "c_123",
  "lat": …,
  "lon": …,
  "online": true
} 

// далее — живые
{
  "type": "position",
  "courierId": "c_123",
  "lat": …,
  "lon": …
}

// ушёл оффлайн
{
  "type": "status",
  "courierId": "c_123",
  "online": false
}                    
```

# 5. Границы контракта

Выше описано, как контракт покрывает FR1–FR5. Сквозные вопросы — аутентификация и авторизация,
жизненный цикл и ошибки WebSocket, краевые случаи дедупа и кэша — сознательно **не** детализируются
здесь, чтобы контракт оставался читаемым. Частично собраны в артефакте 07 с предполагаемым направлением
по каждому.
