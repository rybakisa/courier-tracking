# 1. Масштабируемость

Пять узких мест, каждое — с цифрой из расчётов (артефакт 02). По каждому: что именно упирается, как
это снимаем и где следующий предел. Главная сложность системы, как и зафиксировано в расчётах, —
не объём данных, а **полмиллиона одновременных соединений** и **fan-out в плотных зонах**.

---

# 2. Шардирование потока записи (~75K сообщ/с)

**Что упирается.** 75K сообщ/с на пике, проектно ×2 = 150K (артефакт 02, §2). Один консьюмер и одна
очередь это не вывезут, и — что важнее — нельзя перемешать пинги одного курьера: дедуп по
`(courierId, seq)` и реконструкция маршрута требуют порядка.

**Решение.** Партиционируем лог по `hash(courierId)`. Это даёт два свойства разом: **порядок внутри
курьера сохранён** (все его пинги в одной партиции), а **разные курьеры идут параллельно**. Число
партиций берём с запасом на рост и под параллелизм консьюмеров: 150K сообщ/с по ≈50 Б — это единицы
МБ/с, для Kafka-класса смешная нагрузка; партиции нужны не ради байт, а ради параллелизма обработки и
будущего роста. Live- и history-консьюмеры масштабируются, разбирая непересекающиеся подмножества
партиций (consumer group).

**Следующий предел.** Перекос ключа: мегаполис даёт горячие партиции. Лечится числом партиций кратно
больше числа узлов (дешёвый ребаланс) и, при необходимости, составным ключом. Репартиционирование на
лету болезненно — поэтому партиций сразу с запасом.

---

# 3. Управление ~500K одновременных соединений

**Что упирается.** ≈505K постоянных WS: 300K курьеров + 200K клиентов + 5K диспетчеров (артефакт 02,
§5). При консервативных 20K соединений на узел — это 35–40 gateway-узлов. Соединения **stateful**:
их нельзя просто раскидать round-robin.

**Решение.**

- **Горизонтальный gateway-тир.** Узлы не делят состояние соединений; добавление узла линейно
  поднимает ёмкость. CPU/память на узле бюджетируются под число коннектов, не под RPS.
- **L4-балансировка с affinity.** Раскладка по least-connections / consistent-hashing; реконнект
  по возможности возвращается на тот же узел (resume по `seq`, артефакт 04 §4.1).
- **Региональные gateway (NFR4).** Наблюдатель подключается в регионе курьера — соединение не
  ходит между континентами, а заодно бьётся на независимые по отказу зоны.
- **Дешёвый реконнект.** Сетевые разрывы у мобильных постоянны; resume по `seq` делает
  переподключение бесплатным по данным и позволяет сливать узлы при деплое (connection draining).

**Следующий предел.** Шторм одновременных реконнектов (выпал узел/зона — десятки тысяч клиентов
ломятся разом). Гасится джиттером backoff на клиенте и запасом ёмкости ×2 (те самые 40 узлов против
расчётных 26).

---

# 4. Контроль fan-out для диспетчерских вьюпортов

**Что упирается.** Это самое опасное место по нагрузке. Раздача наблюдателям ≈125K сообщ/с в среднем
(артефакт 02, §2), но опасна не средняя, а **хвост**: в плотном центре в один вьюпорт попадают тысячи
курьеров, и наивная индивидуальная раздача уходит в гигабиты/с на немногих диспетчеров.

**Решение** (композиция паттернов из артефакта 05):

- **Серверная кластеризация** держит **постоянный бюджет ~150 маркеров на вьюпорт** независимо от
  плотности — потолок исходящего объёма на сессию фиксирован.
- **Cell-pub/sub:** публикуем пинг только в его гео-ячейку, доставляем только подписчикам этой
  ячейки — раздача замкнута на пересечение, а не на всех.
- **Дельты, не снапшоты:** в живом канале идут только `enter/move/leave`; полный кадр — один раз
  при открытии вьюпорта (REST-снапшот через CDN).
- **Коалесинг по тику:** несколько движений в ячейке за тик схлопываются в одно обновление.

**Следующий предел.** Очень быстрый пан/зум диспетчера = шквал re-subscribe и пересчёт кластеров.
Гасится дебаунсом вьюпорта и инкрементальной кластеризацией (пересчитываем только затронутые ячейки,
не весь экран).

# 5. Горизонтальное масштабирование живого хранилища

**Что упирается.** Парадокс: по **объёму** live-store крошечный — 300K курьеров × десятки байт
last-known ≈ единицы–десятки МБ, влезает в память одного узла. Упирается не ёмкость, а **пропускная
способность чтения/публикации и гео-роутинг**: тот же стор обслуживает upsert на каждый пинг и
обращения fan-out по ячейкам.

**Решение.**

- **Шардирование по гео-ячейке (S2/H3), а не по `courierId`.** Тогда «все курьеры этой области»
  лежат на одном шарде — запрос вьюпорта и публикация в ячейку локальны, без scatter-gather.
- **Co-location реестра подписок с шардом ячейки:** publish и его подписчики — на одном узле,
  раздача не прыгает по сети.
- **Репликация горячих шардов** под доступность (NFR5): чтения с реплик, отказ узла не теряет
  live-картину (а холодная правда всё равно в логе — реплей).

**Следующий предел.** Горячая ячейка (стадион, вокзал) перегружает один шард. Лечится динамическим
переразбиением ячейки на под-ячейки следующего уровня иерархии (S2/H3 это позволяют бесплатно).

# 6. Партиционирование и TTL холодного хранилища

**Что упирается.** ≈225 ГБ/день, ≈82 ТБ/год (артефакт 02, §3), retention ровно 1 год. Запросы —
строго по курьеру: маршрут за день (FR4) и история за период (FR5). Это **не** аналитика по всем — это
point/range по ключу курьера.

**Решение.**

- **Wide-column стор** (Cassandra/Scylla), партиция-ключ `(courierId, day)`. Тогда «маршрут за
  сегодня» — это **одна** партиция, «история за период» — узкий диапазон партиций по дням. Никаких
  полных сканов.
- **Кластеризация внутри партиции по времени** — точки уже отсортированы, чтение маршрута
  последовательно.
- **TTL = 1 год.** Удаление за пределами года — это не построчный DELETE, а дроп старых партиций по
  времени (дёшево, без compaction-штрафа).
- **Tiering.** Свежие дни на SSD (горячие чтения для разбора споров/выплат), старые месяцы — в
  дешёвый объектный сторадж колоночным форматом (Parquet) под редкие обращения.
- **Компрессия дельтами:** последовательные координаты курьера сжимаются хорошо (соседние точки
  близки) — реальный объём на диске заметно ниже 82 ТБ.

Для аналитических срезов (тепловые карты, агрегаты по зонам), если понадобятся, — отдельная
ClickHouse-проекция из того же лога; операционный путь FR4/FR5 она не трогает.

**Следующий предел.** Курьер-долгожитель с гигантской историей — но партиционирование по дню
ограничивает любую партицию одними сутками, так что размер партиции ограничен сверху по определению.

# 7. Итог

| Узкое место | Цифра (арт. 02) | Чем снимаем | Следующий предел |
|---|---|---|---|
| Поток записи | 75K→150K сообщ/с | Партиции лога по `courierId` | Перекос ключа → больше партиций |
| Соединения | ≈505K, 35–40 узлов | Горизонт. gateway + L4-affinity + регионы | Шторм реконнектов → джиттер + запас |
| Fan-out вьюпортов | до гигабит/с в пике | Кластеризация + cell-pub/sub + дельты | Быстрый пан/зум → дебаунс |
| Live-store | единицы МБ, но throughput | Шард по гео-ячейке + co-location подписок | Горячая ячейка → под-ячейки |
| Cold-store | 82 ТБ/год | Партиции `(courier,day)` + TTL + tiering | Ограничен сутками по определению |

Сквозная мысль: **объём данных нигде не является проблемой** — узкие места все про конкурентность
(соединения, fan-out, горячие ключи). Поэтому и решения однотипны: шардировать по правильному ключу
(`courierId` для записи, гео-ячейка для раздачи) и держать потолок на исходящий объём (кластеризация).
Что из этого мерить в проде и как ловить деградацию — артефакт 07.
