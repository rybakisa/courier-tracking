# 1. Масштабируемость / отказоустойчивость

Узкие места системы — про **конкурентность** (полмиллиона соединений, fan-out в плотных зонах), а не про
объём данных (артефакт 02). Сквозной принцип **отказоустойчивости**: durable-лог — источник правды (при
отказах ничего не теряем, реплеим с оффсета), а живые тиры — stateless либо перестраиваемы, поэтому отказ
инстанса лечится реконнектом/реплеем, без потери durable-данных. По каждому узлу ниже: чем масштабируем и
что происходит при отказе.

---

# 2. Connection Manager — много инстансов, регионально

**Масштаб.** ≈500K постоянных WS (300K курьеров + 200K клиентов + ~1K операторов, артефакт 02 §5) → при
~20K соединений на узел это **35–40 узлов**. Соединения долгоживущие — балансируем при установке (по числу
коннектов), не пер-запрос.

- **Горизонтальный тир.** Узлы не делят состояние соединений; добавление узла линейно поднимает ёмкость;
  CPU/память бюджетируем под число коннектов, не под RPS.
- **L4 least-connections, без sticky-sessions.** WS сам «липкий» (TCP-пайп = узел); реконнект можно принять
  на любом узле (состояние реконструируемо), affinity опциональна и для мобильных ненадёжна.
- **Регионально (NFR4).** Курьер и его наблюдатели подключаются к эджу своего региона → ниже RTT,
  **стабильнее WS и меньше сетевых хопов**, плюс изоляция отказов по зонам.

**При отказе.** Узел умер → его ~15–20K соединений рвутся → клиенты переподключаются (джиттер-backoff) на
живые узлы (L4) → **переподписка + снапшот** догоняет. Durable-данные не теряются (пинги курьеров — в логе).
Шторм одновременных реконнектов гасится джиттером и запасом ёмкости ×2 (40 узлов против расчётных 25).
Межрегиональный failover (потеря целого региона) — отложено, артефакт 08 §5.

# 3. Приём и durability — Kafka

**Масштаб.** 55K сообщ/с пик, проектно ×2 ≈ 110K (артефакт 02 §2). Партиционируем лог по `hash(courierId)`:
**порядок внутри курьера сохранён** (нужно для идемпотентности по `(courierId, installId, seq)` и
реконструкции маршрута), а **разные курьеры идут параллельно**. Live- и History-консьюмеры масштабируются
**consumer-group’ой** (непересекающиеся партиции) и получают сообщения **в порядке партиции**. Партиций
берём кратно больше узлов — дешёвый ребаланс и запас на рост (110K сообщ/с по ≈50 Б — для Kafka смешные
байты; партиции нужны ради параллелизма и порядка, не ради объёма).

**Durability / при отказе.** Пишем с **`acks=all`, `replication.factor = 3`, `min.insync.replicas ≥ 2`**:
курьеру уходит `ack` только когда пинг durable на ≥2 репликах. Отказ брокера/узла → данные на репликах,
продолжаем **без потерь**. Упал или отстал консюмер → **реплей с оффсета**, ничего не теряя. Это и есть
«источник правды», от которого живут обе проекции.

**Следующий предел.** Перекос ключа (мегаполис → горячая партиция) — лечится числом партиций кратно больше
узлов и, при необходимости, составным ключом.

# 4. Контроль fan-out для операторских вьюпортов

**Что упирается.** Самое опасное место по нагрузке — не средняя раздача, а **хвост**: в плотном центре в
один вьюпорт попадают тысячи курьеров, и наивная индивидуальная раздача уходит в гигабиты/с на немногих
операторов.

**Решение** (композиция паттернов из артефакта 05):

- **Серверная кластеризация** держит **постоянный бюджет ~150 маркеров на вьюпорт** независимо от плотности —
  потолок исходящего объёма на сессию фиксирован.
- **Топик-на-ячейку:** обновление уходит только подписчикам этой ячейки — раздача замкнута на пересечение.
- **Полный снапшот вьюпорта каждый тик** (≤150 маркеров, не дельты): кадр крошечный (бюджет кластеризации),
  самокорректирующийся (нет дрейфа при best-effort), без diff-стейта и стабильности id маркеров.
- **Коалесинг по тику:** несколько движений в ячейке за тик схлопываются в одно обновление.

**Следующий предел.** Очень быстрый пан/зум оператора = шквал re-subscribe и пересчётов снапшота. Гасится
дебаунсом вьюпорта; сам пересчёт дешёвый — он ограничен бюджетом ≤150 маркеров (не зависит от плотности).

# 5. Live Service — один узел на регион

**Что упирается (и что нет).** По объёму живое состояние крошечное — ≈30 МБ на 300K курьеров (артефакт 02 §3),
влезает в память одного узла. По нагрузке — 55K upsert/с + чтения/публикации (~50K/с) — это один in-memory
узел (Redis-класс: 100K–1M ops/с). **Ни ёмкость, ни throughput шардирование не требуют.**

- **Гео-ячейка (S2/H3) — in-memory индекс внутри узла, а не ключ шардирования.** «Кто в bbox» и «куда
  публиковать» — локальные lookup’ы; реестр подписок тут же. Никакого сетевого шаффла `courierId → ячейка`.
- **Инстанс на регион (NFR4)** — грубое гео-партиционирование по региону ради латентности и доменов отказа.

**Индекс обновляется точечно, не перестраивается.** Что бы ни лежало под капотом — Redis-native GEO
(один sorted-set, `score` = geohash из lat/lon, `GEOADD` = `ZADD`, O(log N)) или явные S2/H3-ячейки
(`cell→set` курьеров, апдейт O(1), пересечение границы = move между двумя сетами) — пинг трогает **одного**
курьера, а не структуру целиком. На горячем пути нет «перестроения индекса», есть 55K независимых
upsert'ов/с (N≈300K → log2≈18, для in-memory ничтожно). Чтение по вьюпорту (FR3) — `GEOSEARCH … BYBOX`
или перечисление ячеек, покрывающих bbox: O(N_в_зоне + log M), а хвост в плотных зонах срезан серверной
кластеризацией до ≤150 маркеров (§4). S2/H3 при этом выбран не ради скорости индекса, а ради явных
топиков-на-ячейку для pub/sub. Единственное настоящее перестроение — холодный старт реплики через реплей
лога (ниже), вне горячего пути.

**При отказе.** primary упал → тёплая **реплика** (потребляет тот же лог, держит ту же in-memory картину)
промоутится и продолжает; в крайнем случае новый инстанс **реплеит лог** и восстанавливает картину за секунды.
Подписчики при этом на своих CM-сокетах — теряют максимум короткий лаг, durable-данные целы.

**Следующий предел (отложено).** Когда курьеров станет ≫300K или гео-rate перерастёт один узел — тогда
шардируем по гео-ячейке вместе с co-location подписок (артефакт 08). Горячая ячейка (стадион) внутри узла —
не shard-hotspot, а CPU на публикацию; её гасит та же кластеризация.

# 6. Pub/Sub раздача — поведение при отказах

**Транспорт.** Live публикует `(subscriberId, payload)` в **эфемерную шину** (Redis/NATS, артефакт 05 §5);
CM-инстанс подписан на id своих сокетов, шина доставляет туда, где сокет. Доставка best-effort: потеря
самолечится снапшотом при реконнекте; durable-гарантию несёт лог, не шина.

- **Отказ инстанса CM.** Его сокеты рвутся → шина снимает его подписки (на `sub.X` никого) → notify в зазоре
  дропаются (доставлять некуда) → клиент переподключается на новый инстанс **M** → пере-`subscribe` → M
  подписывается на `sub.X`, **шина перенаправляет канал на M**, + свежий снапшот. Live ничего не менял —
  публикует в тот же `sub.X`. Миграции сессии не нужно.
- **Отказ инстанса Live.** Реплика промоутится (см. §5), публикация в шину продолжается; каналы `sub.X` и
  подписки CM не трогаются. Короткий лаг, без потерь.

# 7. Холодное хранилище — wide-column, репликация и шардирование

**Что упирается.** Годовой архив ≈5.5–36 ТБ по политике записи (артефакт 02 §3), retention 1 год. Запросы
строго по курьеру (маршрут за день FR4, история за период FR5) — point/range, не аналитика по всем.

- **Запись по политике (прорежение):** ≈1/мин база, детальнее на активной доставке → держит объём; приём
  lossless (полная детализация короткое время живёт в логе).
- **Wide-column (Cassandra/Scylla), ключ `(courierId, day)`:** «маршрут за сегодня» = **одна** партиция,
  история = узкий диапазон партиций. **Репликация (RF) и шардирование — встроенные** (consistent-hash
  кольцо): линейно добавляем узлы, **нет single point of failure**, отказ узла покрыт репликами. Никаких
  полных сканов.
- **TTL = 1 год** — дроп старых партиций (дёшево, без compaction-штрафа). **Tiering:** свежее на SSD,
  старое — в объектный сторадж (Parquet). **Дельта-компрессия:** соседние точки близки → объём ниже.

Аналитика (тепловые карты, агрегаты), если понадобится, — отдельная ClickHouse-проекция из того же лога;
операционный путь FR4/FR5 не трогает.

**Следующий предел.** Курьер-долгожитель — но партиция ограничена сутками по определению.

# 8. REST API Service — stateless, легко скейлить

Stateless HTTP-фронт → горизонтально за LB, тривиально добавляем инстансы, **любой обслужит любой запрос**.
Обслуживает: тикеты, live-чтения (`/position`, `/viewport` → Live), история (`/route`, `/history` → cold через
History) и **fallback курьера/клиента на HTTP** (`POST /pings` → лог с `acks=all`), когда WS невозможен.
**При отказе** инстанса LB уводит на живой; запросы идемпотентны/ретраибельны (`Idempotency-Key` на батче,
дедуп по `(courierId, installId, seq)`).

# 9. Итог

| Узел | Масштаб | Чем масштабируем | При отказе |
|---|---|---|---|
| Connection Manager | ≈500K conn, 35–40 узлов | горизонт. + L4 least-conn + регионы | реконнект на любой узел + снапшот |
| Лог (Kafka) | 55K→110K сообщ/с | партиции по `courierId` | `acks=all`/RF3 → без потерь; реплей |
| Live Service | ≈30 МБ, ~50K ops/с | один узел/регион + реплики | реплика промоутится / реплей лога |
| Pub/Sub шина | ~50K notify/с | эфемерная, ключ `subscriberId` | best-effort; снапшот при реконнекте |
| Cold-store | ≈5.5–36 ТБ/год | wide-column: RF + шардинг кольцом | реплики покрывают отказ узла |
| REST API Service | чтения + fallback | stateless за LB | LB уводит на живой инстанс |

Сквозная мысль: **объём нигде не упирается** — узкие места про конкурентность (соединения, fan-out, горячие
ключи). А **отказоустойчивость** держится на двух опорах: durable-лог (источник правды + реплей) и
stateless/реконструируемые живые тиры (отказ → реконнект или промоут реплики, без потери durable-данных).
Что из этого мерить в проде и как ловить деградацию — артефакт 07.
