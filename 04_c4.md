# 2. Уровень 2 — Контейнеры

Семь логических контейнеров.
Connection Manager продьюсит пинги в durable-лог.
От него расходятся две ветви:
- горячая (in-memory, для живой раздачи)
- холодная (запись истории по политике).

Живую раздачу Live Service ↔ Connection Manager несёт эфемерная pub/sub-шина.
Чтения и REST-fallback обслуживает отдельный stateless REST API Service.

## 3.2 Live Service

<figure class="schema">
<a href="/schemas/lvl3_live_schema.png" target="_blank" rel="noopener" title="Открыть в полном размере">
<img src="/schemas/lvl3_live_schema.png" alt="Live Service — компоненты" />
</a>
</figure>

Ядро контроля горячих "подписок":
- оператор подписан на ячейку (область карты)
- клиент подписан на своего курьера.

Кластеризация сворачивает плотные ячейки в ≤150 маркеров на вьюпорт. Оператору шлём полный снапшот вьюпорта каждый тик, не дельты:
при бюджете 150 кадр крошечный.

Connection Manager и Live Service общаются только через pub/sub, в обе стороны: Live шлёт **логические**
notify (id подписчиков, не сокеты), а подписки (`subscribe`/`unsubscribe`) приходят в реестр по той же шине
(soft-state с refresh; артефакт 05 §3). `subscriberId` — устойчивый id подписки; где висит сокет,
знает только Connection Manager. Так волатильное «подписчик→сокет» живёт в транспортном тире, а Live остаётся чистым матчингом.

# 4. Пошаговое описание основного сценария

1. Курьер держит постоянный WebSocket
2. Где постоянное соединение невозможно, шлёт fallback по REST
2. Connection Manager принимает сообщение `ping {seq, ts, lat, lon}`
3. Connection Manager продьюсит позицию в лог (`acks=all`, `key=courierId` — пинги одного курьера в одну партицию, чтобы обеспечить порядок)
4. После durable-записи CM отвечает курьеру `ack {throughSeq}`
   - До ack устройство копит неподтверждённое и переотправит при реконнекте
6. Лог читают два независимых консьюмера (партиции по `courierId`), каждый в своём темпе и в порядке партиции
   - Если один из консьюмеров отстал или упал, реплей с оффсета
7. Live Service (горячий путь):
   - обновляет гео-индекс
   - по реестру подписок находит наблюдателей
   - для оператора считает снапшот вьюпорта
   - шлёт данные в Connection Manager
   - CM находит сокет по своему реестру сокетов и пушит в него данные
9. History Service (холодный путь)
   - пишет точки в OLAP-хранилище по политике прорежения
10. История доступна для запросов/аналитики через REST API Service
