# 1. Уровень 1 — Контекст

Система — чёрный ящик, который **только поставляет данные о местоположении**. Назначение
заказов, маршрутизация и ETA — внешние системы вне скоупа; они влияют лишь на то, *кто за кем
наблюдает*, но в потоки данных не входят.

<img src="/schemas/lvl1_schema.png" alt="C4 уровень 1 — контекст" />
</a>
</figure>

| Актор / система | Направление | Взаимодействие |
|---|---|---|
| Курьер | → система | Шлёт своё положение в фоне (WS-ingest, FR1) |
| Клиент | ← система | Следит за **одним** известным курьером (FR2) |
| Оператор | ← система | Следит за **областью карты** — произвольный набор курьеров (FR3–FR5) |
| Система заказов | вне скоупа | Определяет связку «клиент ↔ курьер»; в трекинг не входит |
| Auth / Identity | вне скоупа | Аутентифицирует акторов и выдаёт короткоживущие WS-тикеты; трекинг их только проверяет |

Ключевая развязка уровня контекста — два паттерна доступа у потребителей: **подписка на сущность**
(клиент → курьер) и **подписка на область** (оператор → bbox). Дальше они расходятся в разные
контейнеры.

# 2. Уровень 2 — Контейнеры

Семь логических контейнеров. Connection Manager продьюсит пинги в **durable-лог**; от него расходятся
две ветви — горячая (in-memory, для живой раздачи) и холодная (запись истории по политике). Живую
раздачу Live Service ↔ Connection Manager несёт **эфемерная pub/sub-шина** (не лог). Чтения и
REST-fallback обслуживает отдельный stateless **REST API Service**.

<figure class="schema">
<a href="/schemas/lvl2_schema.png" target="_blank" rel="noopener" title="Открыть в полном размере">
<img src="/schemas/lvl2_schema.png" alt="C4 уровень 2 — контейнеры" />
</a>
</figure>

| Контейнер | Роль | Технология (класс) | Состояние |
|---|---|---|---|
| Connection Manager | Терминация всех WS, продьюсит пинги в лог (acks=all, key=courierId), реестр сокетов + push | WS-сервер (Go/Netty) + L4-LB | Stateful: соединения + сокет-адресация |
| REST API Service | HTTP-фронт: live-чтения (`/position`,`/viewport`→Live), история (`/route`,`/history`→History), fallback-ingest (`/pings`→лог) | Stateless за LB | Stateless |
| Log-брокер | Durable append-only лог, источник правды, реплей, развязка | Kafka / Pulsar / Redpanda | Stateful: партиции |
| Pub/Sub шина | Эфемерная доставка notify Live→CM и подписок CM→Live по ключу `subscriberId` | Redis Pub/Sub / NATS core | Без durability (fire-and-forget) |
| Live Service | Гео-индекс (last-known + cell), реестр подписок, кластеризация, снапшоты вьюпорта, notify; in-memory, 1 узел/регион + реплики | Go-сервис + in-memory индекс (S2/H3) | Stateful: горячая картина (перестраиваема из лога) |
| History Service | Запись в OLAP-хранилище по политике (≈1/мин база, детальнее на доставке), чтение маршрута/истории | Stateless | Stateless |
| OLAP-хранилище | История за 1 год, сортировка/партиции `(courierId, day)`, TTL + tiering | ClickHouse-класс: колоночная OLAP, геофункции (S2/H3) | Stateful: durable |

**Четыре потока данных.**

1. **Ingest (FR1).** Курьер → Connection Manager → **durable-append в лог** (Kafka-продьюсер, `acks=all`,
   `key=courierId`) → `ack` курьеру. `ack` только после durable-записи (NFR2); до него устройство буферит и
   переотправляет. Дубли безвредны — консюмеры идемпотентны по `(courierId, installId, seq)`.
2. **Горячий (FR2, FR3).** Лог → Live Service обновляет гео-индекс, по реестру подписок находит наблюдателей,
   считает снапшот и шлёт **логические** notify через **pub/sub-шину** → Connection Manager (резолвит сокет
   сам) → клиент/оператор.
3. **Холодный (FR4, FR5).** Тот же лог → History Service пишет точки в OLAP-хранилище **по политике прорежения**
   (≈1/мин база, детальнее на активной доставке). Приём lossless: полная детализация короткое время живёт в логе.
4. **Чтение по требованию + fallback.** Всё REST — через stateless **REST API Service**: live-чтения → Live
   Service; история → OLAP-хранилище через History Service; fallback-пинги курьера → durable-лог. Мимо горячего пути.

Почему два консьюмера от одного лога, а не запись «вилкой» в приложении: лог даёт **реплей**. Если Live
Service или OLAP-хранилище отстало/упало — переигрываем с нужного оффсета, не теряя точек. Это и есть
материализация развязки «свежесть ↔ durability» из артефакта 03.

# 3. Уровень 3 — Компоненты

По небольшой диаграмме на каждый сервис: **Connection Manager**, **REST API Service**, **Live Service**,
**History Service**. (Log-брокер, Pub/Sub шина и OLAP-хранилище — инфраструктура, без отдельных компонентных схем.)

## 3.1 Connection Manager

<figure class="schema">
<a href="/schemas/lvl3_cm_schema.png" target="_blank" rel="noopener" title="Открыть в полном размере">
<img src="/schemas/lvl3_cm_schema.png" alt="Connection Manager — компоненты" />
</a>
</figure>

Единственный stateful-тир на пути соединений: держит WS-сокеты, но **не хранит данные домена** (живая
картина — в Live Service, история — в OLAP-хранилище). В «Сессиях» лежит только **состояние соединений**: какой
сокет чей (`courierId` у курьера, `subscriberId` у наблюдателя), жив ли он (heartbeat) и докуда курьер
подтверждён (`last-ack seq` — для resume при rolling-деплое без потери пингов).

С **курьером** сигналы ходят в обе стороны: `ping` внутрь → durable-append в лог → `ack` назад (только после
записи), плюс `config` с частотой, когда курьера наблюдают. С **наблюдателями** тоже двусторонне:
`subscribe`/`viewport` внутрь, `push` наружу. Саму живую раздачу несёт **внешняя pub/sub-шина**: CM публикует
в неё подписки, а назад принимает **логические** notify (кого обновить) — Push-роутер резолвит `subscriberId`
в конкретный сокет по «Сессиям» и пушит в WS. Где висит сокет, знает **только** CM; Live оперирует лишь
`subscriberId` (артефакт 05 §3).

## 3.2 Live Service

<figure class="schema">
<a href="/schemas/lvl3_live_schema.png" target="_blank" rel="noopener" title="Открыть в полном размере">
<img src="/schemas/lvl3_live_schema.png" alt="Live Service — компоненты" />
</a>
</figure>

Ядро контроля fan-out — **гео-ячейка как единица подписки**: наблюдатель подписан на ячейку (клиент — на
ячейку своего курьера, оператор — на набор ячеек вьюпорта), раздача идёт только в пересечение. Кластеризация
сворачивает плотные ячейки в **≤150 маркеров на вьюпорт** — это и есть кадр оператора. **Оператору шлём
полный снапшот вьюпорта каждый тик, не дельты:** при бюджете 150 кадр крошечный, снапшот самокорректирующийся
(нет дрейфа при best-effort), без diff-стейта и стабильности id (артефакт 05 §7).

**Connection Manager и Live Service общаются только через pub/sub, в обе стороны:** Live шлёт **логические**
notify (id подписчиков, не сокеты), а подписки (`subscribe`/`unsubscribe`) приходят в реестр по той же шине
(soft-state с refresh; артефакт 05 §3). `subscriberId` — устойчивый id подписки; где висит сокет,
знает **только Connection Manager** (реестр сокетов). Так волатильное «подписчик→сокет» живёт в транспортном
тире, а Live остаётся чистым матчингом.

**Гео-ячейка здесь — индекс внутри узла, а не ключ шардирования.** При ≈30 МБ живого состояния (артефакт
02 §3) индекс, подписки и кластеризация живут в одном реплицируемом узле на регион — без сетевого шаффла
`courier→ячейка`. Шардинг по ячейке понадобится только при кратном росте (артефакт 05 §6).

# 4. Как это работает под капотом — по акторам

Те же контейнеры из §3, но «обычными словами»: что происходит шаг за шагом.

## 4.1 Курьер отправляет положение (FR1)

1. Курьер держит постоянный **WebSocket** (`/v1/stream/courier`). Где постоянное
   соединение невозможно — шлёт пачкой по **REST** (`POST /couriers/{id}/pings`, фоллбек через REST API Service).
2. **Connection Manager** терминирует соединение, принимает кадр `ping {seq, ts, lat, lon}`.
3. Connection Manager **сам продьюсит** пинг в лог (`acks=all`, `key=courierId` — пинги одного курьера в одну
   партицию, по порядку). Отдельного Ingest-сервиса нет.
4. Только **после** durable-записи CM отвечает курьеру `ack {throughSeq}`. До ack устройство копит
   неподтверждённое и переотправит при реконнекте — на приёме ничего не теряется.
5. Дубли (от переотправок) безвредны: консюмеры **идемпотентны по `(courierId, installId, seq)`** и читают
   лог в порядке партиции — отдельный дедуп-стор не нужен.
6. Частота отправки адаптивная: **4 с**, пока за курьером следит клиент (CM шлёт `config`), иначе **10–60 с**.

## 4.2 Поток из лога расходится на два пути

7. Лог читают два независимых консьюмера (consumer-group, партиции по `courierId`), каждый в своём темпе и
   **в порядке партиции**; применяют **идемпотентно по `(courierId, installId, seq)`** (дубль/устаревшее — no-op).
8. **Live Service** (горячий путь) обновляет гео-индекс курьера, по реестру подписок находит наблюдателей,
   считает снапшот вьюпорта и шлёт **логические** notify в Connection Manager (кого обновить); CM сам находит
   сокет по своему реестру сокетов.
9. **History Service** (холодный путь) пишет точки в **OLAP-хранилище** **по политике прорежения** (≈1/мин база,
   детальнее на активной доставке).
10. Если консьюмер отстал или упал — **реплей** с оффсета, без потерь (лог — источник правды).

## 4.3 Клиент следит за своим курьером (FR2)

1. **Первая отрисовка мгновенно**: `GET /couriers/{id}/position` (через REST API Service) — последняя точка из Live Service.
2. Открывает **WebSocket** (`/v1/stream/client`) и шлёт `subscribe {courierId}`; CM публикует эту подписку в Live Service через **pub/sub**.
3. Эта подписка — и есть **сигнал «наблюдают»**: курьер переводится в горячий режим (4 с).
4. Сервер шлёт `snapshot` (первый кадр), дальше `position` по мере пингов; ушёл оффлайн → `status {online:false}`.
5. Плавность «как в такси» — **клиентская интерполяция** между кадрами; сервер не обязан слать суб-секундно.

## 4.4 Оператор смотрит область карты (FR3)

1. Оператор открывает **WebSocket** (`/v1/stream/operator`).
2. **Первичный кадр**: `GET /viewport?bbox=&zoom=` (через REST API Service) — кластеры + одиночные маркеры из Live Service.
3. По WS шлёт `viewport {bbox, zoom}`; CM публикует подписку (ячейки) в Live Service через **pub/sub**. Дальше
   оператор получает **полный снапшот** (`clusters`, ≤150 маркеров) **каждый тик**, не дельты.
4. Live Service по гео-индексу находит курьеров в bbox и сворачивает плотные зоны в кластеры (**≤150 маркеров**
   под текущий zoom) — это и есть кадр; самокорректируется каждым снапшотом.
5. «Горячими» (4 с) становятся **только** индивидуально отрисованные курьеры; наблюдение оператора частоту
   **не** поднимает — ему хватает ≤1 мин.

## 4.5 Чтение маршрута и истории (FR4, FR5)

1. Оператор запрашивает `GET /couriers/{id}/route?date=` или `GET /couriers/{id}/history?from=&to=`.
2. Запрос идёт через **REST API Service** → **History Service** → **OLAP-хранилище** (партиции `(courierId, day)`);
   прошлые дни immutable (агрессивно кэшируются заголовками на клиенте), сегодня дополняется → короткий кэш.
3. Запрос за пределы года retention → `410`.
